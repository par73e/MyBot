# Friday 业务接入可行性研究

研究日期：2026-10-23，Asia/Shanghai。

研究基线：当前 `main` 的 `3ecd7a4`，源码入口 `reasonix-assistant-v1.39.10/`。这是技术可行性与方案评估，不是实现、上线或真实通知验收。没有接入个人邮箱、日历或课程表，没有更改生产配置、任务、记忆或模型。

## 结论与范围

六项主要需求都有技术实现路径。天气、本地课程表、晨间聚合及明确作息计划可在现有 Go 服务上扩展。邮箱需先确定服务商和持续授权方式；本次腾讯服务器默认网络访问 Google 的两个相关地址失败，Gmail 与 Google Calendar 因此只能判断为有条件可行。新闻可以实现有来源的重点新闻精选，但不能把 RSS 顺序当作全网热度排名。

| 板块 | 判断 | 主要新增工作 | 前置条件 |
| --- | --- | --- | --- |
| 天气查询与播报 | 可行，复杂度低 | 天气适配器、地点解析、缓存与数据时间 | 确认城市、选择来源 |
| 邮箱检查与通知 | 可行，但 Gmail 联网有阻碍；复杂度中高 | 授权、增量同步、事件存储、分析与通知去重 | 确认邮箱服务商；授权；验证服务进程联网 |
| 国内／国际／AI 新闻 | 可行，复杂度中 | 来源采集、事件归并、时效校验、中文摘要 | 确定范围和来源；部分来源另需订阅 |
| 当天课程提醒 | 可行，复杂度低至中 | 结构化导入、学期与周次计算、调课例外 | Sir 提供课表、学期第一周日期和节次时间 |
| 晨间综合简报 | 可行，复杂度中 | 数据聚合、部分失败、发送去重和补发时效 | 起床时间；至少一个有效数据源 |
| 白天／夜间作息流程 | 可行，复杂度中 | 持久模式、临时覆盖、有效期和恢复 | 每周作息及临时调整语义 |

上述复杂度是基于源码审查的工程判断，不是工期或供应商承诺。可选项另见文末。

## 已核实的项目能力

- `internal/assistant/tasks.go` 的 `makeJob` 已将 reminder 与 automation 分开；automation 使用独立 Agent、`read-only` 权限与结构化通知决策。
- `internal/heartbeat/schedule.go` 已有带时区的 daily／weekly 等日历调度，能按星期分组设定不同时间。
- `internal/heartbeat/lanes.go` 将固定提醒与 AI 分析分开执行；同一分析通道仍串行，慢来源可能拖延其他分析任务。
- `internal/cli/heartbeat_runner.go` 对一次分析设置十分钟超时；抓取数据应有更短的单来源超时，不能依赖这个总超时兜底。
- `internal/assistant/context.go` 每轮加载有效记忆和待办，可供模型综合判断通知价值。
- `internal/assistant/tools.go` 的 `allowMutation` 禁止后台分析修改个人记忆和调度；增量游标和来源状态需要宿主代码管理。
- `internal/assistant/notifications.go` 已有持久发送记录，确认发送成功后可以只修复会话导入；外部平台发送不确定时仍不能承诺绝对不重不漏。
- `internal/boot/web_search.go` 和 `internal/websearch/search.go` 有搜索工具入口，但是否可用取决于 provider 的真实搜索能力；此次没有测试 Friday 线上模型的搜索请求。

这些能力可复用。现有框架没有自动具备邮箱游标、课程周次、新闻去重或作息状态；仅增加提示词不足以稳定完成全部需求。Codex 中已经连接的 Gmail／Calendar 工具，也不等于云端 Friday 已有同样授权和连接。

## 本次网络验证

于北京时间约 13:24—13:26，从腾讯服务器发起公开、无凭据的读取。第二轮 curl 使用 6 秒连接超时、16 秒总超时。没有读取个人邮件或下载真实聊天。

| 目标 | 实测结果 | 能证明的范围 |
| --- | --- | --- |
| Open-Meteo 上海示例坐标天气 | HTTP 200，返回当天日期、最高／最低温与降水概率字段 | 当时服务器可调用该公开预测接口；不证明本地预报精度 |
| 中新网要闻 RSS | HTTP 200，可解析 30 条；前三条日期均为 10 月 23 日 | 该订阅当时可访问且有当天内容 |
| 中新网国际 RSS | HTTP 200，可解析 30 条；前三条日期均为 10 月 23 日 | 同上；不证明全天持续可用 |
| The Rundown 首页 | HTTP 200；首页 HTML 未发现 RSS／Atom alternate 链接 | 网页访问可行；不能据此断言全站没有 RSS 或公开 API |
| `gmail.googleapis.com` 与 `oauth2.googleapis.com` | Python 请求失败；curl 连接超时，未取得 HTTP 响应 | 默认 shell 网络下这两个地址当时不可用；没有完成授权 API 验证 |

Google 结果不是完整网络诊断：没有验证所有域名、服务进程的专用代理、其他网络出口或长期稳定性。若选 Gmail，实施前应在实际服务身份与网络配置下再次测试授权、刷新令牌和邮箱 API。

## 1. 天气查询与播报

**可实现的行为。** 支持随口查询某城市天气；晨间播报当天温度范围、天气、降雨概率及简短出门建议。相同地点使用同一个适配器和缓存，避免聊天与早报形成两套结果。

**来源选择。** Open-Meteo 是已完成无密钥实测的起步方案，提供所需日预报字段；其免费接口限非商业用途、每天 10,000 次且没有可用性保证，使用时保留来源归属。[预报字段](https://open-meteo.com/en/docs)、[价格及条件](https://open-meteo.com/en/pricing)。和风天气也是候选，需要账号、项目及凭据，支持 JWT；当前天气及基础服务价目表首 50,000 次／月为免费档，后续按量计费。[接入](https://dev.qweather.com/en/docs/start/)、[鉴权](https://dev.qweather.com/en/docs/configuration/authentication/)、[价格](https://dev.qweather.com/en/docs/finance/pricing/)。此次没有和风账号，未完成其真实 API 请求，也未比较两家预报准确性。

**实现建议。** 宿主提供结构化天气工具；输入只允许地点、日期等业务参数，不允许模型指定带凭据的任意 URL。返回来源、地点、预测日期、取得时间、单位和缓存状态。缓存建议 30—60 分钟，失败时只使用带明确时间的有限旧缓存。

**成本判断。** 单地点、半小时取数、每次两类请求的示例规模是每天最多 96 次、30 天约 2,880 次，低于上述基础额度；实际计费仍取决于所选产品、调用次数和未来条款。取数无需调用模型，模型仅在回答或汇总时组织语言。

**需要 Sir 提供。** 默认城市；旅行时是按明确指定城市切换，还是另设临时地点偏好。

**验收重点。** 地点重名、时区、日期、单位、过期缓存、网络失败；不能把“未取得降雨数据”说成“不下雨”。

## 2. 邮箱检查与重要邮件通知

**可实现的行为。** 清醒时每 15／30 分钟同步变化；有新候选邮件时由模型结合有效记忆判断是否通知，夜间积累到晨间简报。广告通常不推送，但不将广告分类做成无法覆盖的永久丢弃规则。邮件未读状态不等于新邮件，已读线程仍可能产生新回复。

**Gmail 路线。** 使用只读 OAuth 权限与离线刷新令牌；按 `historyId` 增量读取并分页，游标失效返回 404 时重建同步基线。不能仅以“上次检查时间 + 未读”过滤。[增量同步](https://developers.google.com/workspace/gmail/api/guides/sync)、[服务端授权](https://developers.google.com/workspace/gmail/api/auth/web-server)。官方额度使用 quota units，个人低频同步预计不是主要瓶颈，但应按实际邮件量和当前配额计算，不能把所有调用永久视作免费。[额度](https://developers.google.com/workspace/gmail/api/reference/quota)。

**当前障碍。** 服务器默认网络无法完成 Google 请求，需要先验证可持续的联网路径。若选在 Mac 取数再提交事件，Mac 睡眠或关机会中断积累；它不满足无条件全天常驻的假设。也可以评估独立常驻取数端，但这会增加部署和运行成本，尚未选型。

**授权持续性。** Gmail 只读权限属于 restricted scope；个人使用存在审核例外，但不能把个人自用结论推广到公开服务。OAuth 项目若保持 External／Testing，相关刷新令牌通常七天失效，不能据此实现长期无人值守。[权限分类](https://developers.google.com/workspace/gmail/api/auth/scopes)、[个人使用例外](https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification)、[令牌有效期](https://developers.google.com/identity/protocols/oauth2#expiration)。

**其他邮箱。** 若实际使用 Outlook，Microsoft Graph 支持按文件夹 delta 增量同步，可另做适配器；QQ／163／学校邮箱则先核实其官方 API 或 IMAP、授权码及服务器网络条件。本次未测试这些账号，不将 Gmail 方案当成所有邮箱通用实现。[Outlook 增量接口](https://learn.microsoft.com/en-us/graph/api/message-delta?view=graph-rest-1.0)。

**实现建议。** 程序将来源变化持久化，提交事件成功后再推进游标；模型只读取有界的新增候选。记录“已获取、已分析、已单独通知、已进入简报”等不同状态，避免静默后丢失晨间汇总素材。默认只读，不改变已读状态或发信。凭据由宿主管理，不进入模型上下文。外部邮件内容仅作数据，不能据其内容执行命令或创建任务。

**成本判断。** 假设清醒 16 小时，15 分钟一次约 64 次／天，30 分钟一次约 32 次／天。没有新变化时应只做 API 检查，不启动模型；当前 automation 会启动 Agent，因此需新增宿主取数与事件触发逻辑。模型费用取决于实际新邮件量与正文长度，现阶段不能给出可信固定月费。

**需要 Sir 提供。** 邮箱服务商、需要检查的文件夹／账号、起床后的检查间隔；具体授权在实施阶段进行。

**验收重点。** 同一线程新增回复、分页中断、游标失效、令牌撤销、重启恢复、静默后晨报可见、重复通知；取数失败不能汇报为“没有重要邮件”。

## 3. 国内、国际及 AI 新闻

**可实现的行为。** 每早生成少量有来源、有日期的重点新闻及 AI 动态，中文总结，同一事件多来源合并。国内／国际范围及数量尚未由 Sir 最终确定。

**已验证来源。** 中新网官方列出要闻、国内、国际等 RSS，本次服务器真实读取的要闻与国际订阅都可解析且有当天更新，适合做第一批来源。[官方订阅目录](https://www.chinanews.com.cn/rss/)。RSS 提供稿件，不提供统一的全网热度指标；如需“微博／知乎等平台热搜排名”，要另行核查平台接口和供应商。

**The Rundown AI。** 官网明确提供 AI 新闻、公开 newsletter 页面及邮件订阅，本次网页可访问；未确认稳定公开 API／RSS。可优先评估公开页面定点抓取，或在 Sir 自行订阅并接入邮箱后，从收到的 newsletter 取材。[官网](https://www.therundown.ai/)。后者依赖邮箱可用性，并受其实际投递时间影响。英文新闻可以翻译摘要，但应保留原文链接；涉及重要技术结论时再核实其指向的原始发布。

**不适合的默认选择。** NewsAPI 的免费 Developer 档仅允许开发测试、文章延迟 24 小时，不能直接作为 Friday 常驻生产新闻源；其当前 Business 月付价为 449 美元，对这一私人助理场景成本偏高。[官方价格与限制](https://newsapi.org/pricing)。

**实现建议。** 优先少量固定来源：国内／国际 RSS + AI newsletter／官网；通用搜索用于补充核实，不能当作已验证的稳定订阅。采集保留 canonical URL、来源、发布时间、发现时间；先按 URL／正文摘要去重，再进行同事件归并。来源迟到可进入下一次汇总，不以“今天抓到”冒充“今天发生”。来源失效时跳过对应部分或说明情况，不补造条目。

**成本判断。** RSS 抓取本身不产生模型费用；模型费用主要来自条目筛选、归并和中文摘要。网页解析的维护成本高于规范 RSS，需要限制来源数量。无需为每篇文章单独启动一次完整 Agent。

**需要 Sir 提供。** 国内／国际范围、AI 比重、大致篇幅；The Rundown 是否作为固定来源还是候选。

**验收重点。** 旧闻重发、不同站点同一事件、发布时间缺失、时区、来源失败、无法打开原文；连续无重大更新时不强行凑数。

## 4. 课程表与当天课程提醒

**可实现的行为。** 导入本学期课程，晨间列出今天的课程、上课时间和教室；可另加明确的课前固定提醒。先支持 Sir 提供的课表，学校账号自动同步另立范围。

**数据形式。** 表格、文本或 ICS 适合结构化导入；截图可人工／模型辅助识别后生成待核对数据，不把 OCR 结果直接当作已确认安排。iCalendar 已有重复规则与排除日期，可表达许多周期与停课例外。[RFC 5545](https://www.rfc-editor.org/rfc/rfc5545)。

**实现建议。** 以学期第一周锚点、周次范围／单双周、星期、节次、教室及例外日期计算实际课程实例。截图识别只负责提取，程序计算日期。调课用明确实例的覆盖／取消记录，优先于原周期；学期结束自动失效。不能仅将一学期课表塞进长期记忆，让模型每天猜今天第几周。

**时间语义。** “今天有什么课”按北京时间自然日解释，不能沿用聊天会话的 06:00 分日。如果凌晨 05:30 发简报，课程与天气仍属于当天自然日，即使聊天会话标题属于前一天。

**成本判断。** 本地课表不需要第三方付费 API；导入识别可能调用模型，日常周次和课程实例计算无需模型。晨报的文字整理可以与其他板块合并。

**需要 Sir 提供。** 课程表、学期第一周起始日期、各节上课时间；已知的单双周、调休及停课安排。

**验收重点。** 开学首周、单双周、考试周、节假日调课、临时换教室、无课日、学期结束；未确认的条目标为待核对。

## 5. 晨间综合简报

**可实现的行为。** 根据星期分别设定起床时间，汇总天气、夜间重要邮件／信息、新闻、当天课程及待办。可以先实现天气 + 课程 + 待办的小版本，邮箱或新闻以后再接入。

**实现建议。** 到点先读取／刷新有界数据快照，再由一次模型分析组织简报，走已有微信发送及当天会话导入入口。每个来源带状态和时间；一个来源失败不阻止其余内容。以 owner + 自然日 + 简报类型生成持久发送标识，确保重启或重试不生成第二份同日简报。

**新增部分。** 需要简报聚合器、每日生成记录、来源覆盖范围、发送检查点和过时补发策略。现有“后台历史最近结果”不能替代这些记录；现有日历任务可能补执行最近时点，晨报必须另判断现在补发是否仍有意义。

**边界。** 起床时间只是计划值，不代表系统知道 Sir 已醒。实际醒来触发可通过前台“我醒了”明确指令实现，未来可再接设备信号。先播报文字；如 Sir 的“播报”特指微信语音，需要另研究 TTS、音频格式与当前微信发送通道支持，此研究不把语音视为已确定范围。

**成本判断。** 基础频率约每天一次简报分析，另加实际查询与补充请求。抓取可并发设短超时，模型汇总保留在现有通道，避免常驻浏览器和无变化时重复调用模型。

**需要 Sir 提供。** 周一至周日的计划起床时间；篇幅；失败来源如何显示；错过多长时间后不再补发。

**验收重点。** 无新邮件、无课、来源部分失败、起床时间临时变化、跨 06:00、重启补发、发送失败与已发送后会话导入修复。

## 6. 作息、白天轮询与夜间积累

**可实现的行为。** 保存每周默认作息，夜间持续取数但减少打扰，起床汇总，白天按间隔检查；支持“今天晚一小时起床”“未来三天旅行”等临时覆盖后自动恢复。

**实现建议。** 用宿主可解析的作息配置及带 starts_at／expires_at 的临时覆盖计算当前阶段。默认计划 + 当前有效覆盖，不破坏性改写默认值；覆盖失效后自然恢复。可由已有前台工具扩展来修改计划，后台只读取和执行。

**程序与模型分工。** 程序可靠处理取数时间、去重、恢复和明确的勿扰约束；模型结合有效记忆判断某条新信息是否值得通知以及详略，不为每个新闻或发件人都写死价值规则。若 Sir 明确要求“今晚一律不打扰”，应由程序执行该约束，不能让模型自行解释是否破例。

**关键限制。** 现有普通 interval 本身不理解睡眠窗口；需要宿主在窗口外跳过分析或使用独立取数计划。无变化时不调用模型，不能用“每 15 分钟开启 Agent 再让它返回静默”代替低成本检查。

**需要 Sir 提供。** 默认起床／睡眠计划、夜间是否允许任何类型的即时提醒、临时覆盖作用范围；明确时间的已有固定提醒不应被无意取消。

**验收重点。** 周末、跨午夜窗口、重启、临时覆盖到期、多项临时偏好冲突、已醒指令；不能根据没有聊天就推断 Sir 已睡。

## 共用建设与推荐推进顺序

共用建设建议是一个宿主管理的业务数据层：来源适配器 → 游标／事件缓存 → 有界候选数据 → 模型判断／晨报聚合 → 已有发送入口。将“同步成功”“分析完成”“已通知”“已进入晨报”分别记录，网络失败和模型失败也分别记录。游标提交、分页和去重由程序保证；外部内容不能修改宿主权限、收件人或个人状态。

没有必要在第一版引入消息队列集群或常驻浏览器。可先扩展当前 Go／SQLite 的小规模单用户实现；新来源的网络读取不应占用数据库事务或个人状态锁。已有 AI 分析串行通道需要限制批次和单来源等待，容量仍须以真实邮件量与压测验证，不能根据服务器空闲就承诺可同时运行任意业务量。

建议顺序是：

1. 先验证邮箱服务商与联网条件，同时接天气和本地课表。
2. 做天气 + 课程 + 待办的最小晨报，并落实默认作息与临时覆盖。
3. 接邮箱的事件积累、价值判断与晨报汇总。
4. 接国内／国际 RSS 和 AI 新闻，复用同一事件／去重／简报链路。

这是研究建议，不是已经获得的实施授权。下一步规格需要确定：城市、邮箱服务商、课表、每周作息、新闻范围。无需在决定开发顺序之前先授权全部外部账号。

## 可选功能的初步可行性

| 功能 | 判断与建议 | 尚缺的证据／条件 |
| --- | --- | --- |
| Google Calendar | 有条件可行；先只读同步日程，处理删除、重复事件与增量游标失效 | OAuth 和 Google 联网；尚未测试日历 API 或账号 |
| GitHub 直接订阅 | 可行；可从账号通知或指定仓库的 issue／PR 更新取数 | 需要选定范围和 token 权限；与邮箱同一事件需跨源去重 |
| 直播／内容更新 | 平台确定后评估；收到现有通知邮件可先复用邮箱链路 | 未指定平台／主播；不能承诺任意平台都有可靠官方订阅 |
| 服务器巡检 | 可行；固定的只读指标采集，再判断是否通知 | 巡检目标、阈值和已有监控清单；巡检不包含自动修复 |
| Mac 任务状态 | 有条件可行；需要 Mac 侧常驻采集并向服务发送状态 | 本地桥接、身份验证、任务类型；Mac 睡眠／关机时不可保证实时 |
| 每日复盘／主动建议 | 可行；复用待办、有效记忆与有界历史 | 完成记录可信度、范围及发送时间；不能根据“已提醒”推断事情已完成 |

Google Calendar 官方支持 `syncToken`，失效时以 410 要求重建同步；个人规模通常远低于当前标准配额，但未来计费政策需在实施时重核。[同步说明](https://developers.google.com/workspace/calendar/api/guides/sync)、[额度和计费说明](https://developers.google.com/workspace/calendar/api/guides/quota)。

GitHub 通知接口提供条件轮询和 `X-Poll-Interval`，当前文档注明该通知接口仅支持 classic PAT，不能假设任意 fine-grained token 或 GitHub App 都可使用；指定仓库读取可另按对应接口权限设计。[官方通知接口](https://docs.github.com/en/rest/activity/notifications)。

直播的可行性差异很大：例如 Twitch 有 `stream.online` 事件，但仍需配置开发者认证与订阅传输；B 站本次可查到的官方直播开放平台资料面向开发者签名和主播互动接入，未验证其提供“任意关注主播开播”的通用订阅能力。[Twitch 事件](https://dev.twitch.tv/docs/eventsub/eventsub-subscription-types)、[B 站官方开放文档](https://open-live.bilibili.com/document/849b924b-b421-8586-3e5e-765a72ec3840)。此次没有接入或测试第三方收费直播 API。

## 实施前应通过的共同验收

- 每项至少验证一次真实取数，再验证模拟故障、重启与重复事件；公开接口 HTTP 200 不等于个人账号接入完成。
- 故障、没有变化与没有重要内容必须是不同状态；失败不能伪装成“没有”。
- 持久游标分页安全，通知与晨报有独立记录；模型失败不丢事件，发送失败不重新取数或重复生成内容。
- 课程／天气自然日、邮件原始时间、聊天 06:00 日期归属分别处理。
- 不改变 qwen3.8-flash 的现有业务配置；费用先观察实际请求与 token 用量，再形成月费估算。
- 最终微信端验收需要在另行明确的实施范围内完成，本次未向真实微信发送任何研究或测试消息。
