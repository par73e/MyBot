# 课程模块技术研究：固定预设与顶层作息

后续更正：用户明确要求所有自动事件统一经过顶层作息门控，并选择每次课前10分钟提醒。本文保留最初固定预设研究过程；后续实现及验收见 `reasonix-assistant-v1.39.10/verification/ROUTINE_COURSES.md`，以该文档为准。

日期：2026-10-25。研究基线：`44e0d848cd742a268e57ed69cd7f40fcc1f589c8`。

这是源码研究和本地隔离验证，不是课程功能实现或部署报告。没有修改业务代码、生产配置、课表、记忆或调度，没有调用模型 API、发送微信或修改服务器。本轮仅新增本研究文档；验证文件在 OS 临时目录。

## 已确定的产品规则

- 课程自动运行必须受统一 Heartbeat 作息约束；作息是课程自动任务的顶层门控。
- 课程预设是固定钟点。例如周一 10:00、周二 08:00；推迟作息起点不移动这些预设。
- 作息为 08:00–24:00 时，08:00 预设可触发；改为 09:00–24:00 后，08:00 预设当天跳过，不在 09:00 补发，10:00 预设仍正常。
- 本轮不再采用此前“课程提醒独立于作息”的设计。手动问课程仍是普通用户对话，不受自动任务窗口限制。
- 服务进程常驻；作息窗口限制自动执行，不是每天启停 systemd 服务。

## 源码结论

源代码均在 `reasonix-assistant-v1.39.10/` 下。

| 入口 | 当前行为 | 课程接入方式 |
| --- | --- | --- |
| `internal/assistant/heartbeat_config.go: TriggerBounds` | `routine_bound=true` 时先求当天作息窗口；固定 `clock` 早于窗口起点直接返回无效，等于结束时间也无效 | 可直接复用，开始包含、结束排除 |
| `internal/assistant/heartbeat_mutations.go: applyHeartbeatTrigger` | 填写 `clock` 会先把 `RoutineBound` 改为 false，再应用显式 `routine_bound` | 课程触发器必须强制保持 true；不能只依赖 Agent 正确填参 |
| `internal/assistant/heartbeat_prepare.go: prepareModuleTrigger` | 在合法时间内创建日期实例和模块任务 | 复用每日实例与去重，不新增课程私有计时器 |
| 同文件 `moduleTriggerTime` | daily 默认允许在预设后一小时内创建实例 | 课程要显式采用较短触发容差，避免照搬一小时默认值 |
| `internal/assistant/heartbeat_runtime.go: Allows` | 执行时读取最新配置，检查窗口、启停与发生实例 | 课程任务携带 `ModuleID`、`TriggerID`、`OccurrenceID`，走这条门控 |
| `internal/heartbeat/admission.go: runAdmitted` | 模块运行期间每秒复查门控，关闭后取消运行 | 可直接复用 |
| `internal/cli/heartbeat_conversation.go: SendRun` | 模块实际发送前取得会话锁，再复查许可 | 可复用，已提交给网络的请求不能撤回 |

固定星期和钟点的需求已经能用 daily + weekdays + clock 表达，不需要新建“相对课程开始时间”调度模式。后者仅在未来明确要求按每节课自动倒推提醒时间时另行设计。

## 建议的实现

### 1. 课程数据和工具

新增 `CourseService`，通过现有 Repository 的 SQLite 事务存储学期、节次、周期课程和课程例外。使用独立实体种类，不挤进个人记忆或逐节创建个人待办。

新增 `assistant_courses`：提供配置状态、指定日期的实际课程、下一门课程、导入与例外修改。写入使用 revision，后台只允许读取。导入先校验学期锚点、周次、单双周和节次时间；信息不全不能将“未知”当成“无课”。查询按北京时间自然日，不采用聊天 06:00 分日。

### 2. 模块执行链路

注册 `course_briefing`（今日课程）与 `course_reminder`（按预设时刻查询下一门/即将开始的课）。两者复用 CourseService，区分提示词、查询范围与通知契约。当前固定钟点仅决定何时执行模块，不自动推算每门课的提醒时刻。

建议第一版沿用现有 Agent 模块通道：

`统一 Heartbeat → 门控 → 日期执行实例 → 后台 Agent → assistant_courses 实际查询 → 程序核对查询回执和通知结果 → 发送前门控 → 微信 → 当天聊天记录`

课程时间、周次和例外由程序计算，Agent 只理解语境和整理文字。今日课程模块无课时可简短报告无课；课前提醒没有符合范围的课程时静默，数据缺失或查询失败必须记录为缺失/失败，不能声称无课。自动课前提醒的精确查询范围需结合实际课表和用户预设确定，不在本研究中假定提前量。

模块应有独立的 course 后台权限范围，只开放课程、记忆/待办/历史的必要只读查询；禁止后台修改课表、作息和个人任务。参考现有天气后台读取回执，要求本次实际查询，防止直接复述旧聊天课程。

### 3. 预设如何保存

不同星期钟点不同，用多个已有 daily 触发器即可，避免新增另一份每周时钟。例如未来模块注册后，周一触发器的核心参数如下；这是建议配置，不是当前可执行配置：

```json
{
  "trigger_id": "courses_monday",
  "mode": "daily",
  "weekdays": ["monday"],
  "clock": "10:00",
  "routine_bound": true,
  "modules": ["course_briefing"],
  "catch_up_seconds": 60
}
```

真正写入仍需 `action=set_trigger` 和最新 revision；周二同理，钟点为 08:00。相同钟点的星期可以合并到同一触发器。当前最多 32 个触发器，足够一个按星期配置的简单课程预设；不能据此宣称支持任意数量的逐节课程计划。

课程模块选入触发器时，后端校验必须要求 `routine_bound=true`，并在修改固定时间后保留绑定；全局配置校验也拒绝课程脱离作息。已有天气/邮件触发器不因新增课程而自动改动，运行计划和模块启用也不在迁移时擅自开启。

### 4. 补发与过期

区分两件事：

- 预设位于作息窗口外：直接无效，不挪到窗口起点，也不创建待补发通知。
- 预设位于作息窗口内：轮询有正常秒级误差，需要短触发容差。建议课程使用 60 秒，而不是现有 daily 默认的一小时；该值是设计建议，不是已生效配置。

模块任务还需要独立的投递截止，并取它与作息结束的较早值；具体通知有效期在实现时依据简报/课前提醒分别确定。所有重试受最新窗口和有效期约束，不能把过时提醒留到以后重新打开窗口时发送。临时推迟作息后，已生成未发送的旧任务也必须再次门控；对不再有效的任务保存跳过原因。

### 5. 可观测性与去重

复用稳定的每日发生实例身份、任务历史、通知 outbox 和发送不确定性处理。补充可见的“不触发原因”：预设早于作息、当天禁用、没有课程、课表未配置、查询失败、投递失败。当前 `runs` 主要列出已经生成任务的运行历史；根本没创建任务的跳过情况需要增加有效预设预览或有界跳过记录，不能声称已有完整记录。

课表有 revision 和例外覆盖；发送前检查课程实例是否取消、换时间或换教室。若数据已经过时则重新生成或跳过，避免发送旧安排。每次变更不直接使用配置 revision 作为新的通知身份，以免仅修改配置便重复推送。

## 需要修改的代码位置

1. 新增 `internal/assistant/course*.go`：数据、校验、日期解析、工具、模块提示词/回执。
2. `heartbeat_config.go`、`heartbeat_prepare.go`：模块目录与任务构造；新模块缺失时兼容迁移且不擅自开启。
3. `heartbeat_mutations.go`、`heartbeat_validate.go`、`heartbeat_tool.go`：固定预设、强制作息绑定、容差与有效状态展示。
4. `internal/boot/assistant.go`、`prompt_policy.go`：工具注册、前后台权限和对话规则。
5. `internal/cli/heartbeat_runner.go`：课程后台范围、查询回执校验和结果契约。
6. `heartbeat_runtime.go` 和发送前课程校验：最新窗口、课程版本、过期与跳过原因。

## 本地隔离验证结果

使用 Go 1.26.10，通过 `go test -overlay` 临时加入研究用例。调用现有实际工具设置函数、TriggerBounds、Prepare、JobStore 和 Allows；仅用已注册天气模块作为调度占位，完全不执行天气或课程业务，也不启动 Agent 和发送器。

9 个窗口场景均通过：预设前不运行；周一10点触发；周二8点等于窗口开始可触发；窗口改9点后8点跳过；10点仍触发；结束时间排除；窗口之前不运行；禁用日不运行；仅某日推迟同样跳过8点。

另外3组通过：已生成任务在窗口变更后被门控拒绝；已完成实例恢复后不重复创建；固定clock默认脱离作息/显式绑定成功，以及现有一小时补执行行为的确认。

首轮验证中，研究用例给“禁用日”同时传了起止时间，被现有校验正确拒绝；修正测试数据为禁用日省略时间后，上述全部通过。没有为使测试通过修改产品代码。
