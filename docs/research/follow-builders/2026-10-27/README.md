## 最小适配及局限

1. **运行环境与网络。** 服务器原本没有 Node。新增独立运行时后，原版 `fetch` 访问 raw.githubusercontent.com 仍然超时；现有 mybot-proxy 日志显示该域名命中 DIRECT。没有改代理规则，而是用 `github-transport.cjs` 将允许的 8 个 feed/提示词 URL 转为同仓库的 GitHub Contents API raw 响应，经既有本地代理访问。每个请求最多 15 秒，只允许固定公开路径，不读取或使用 GitHub token。
2. **调用方式。** `run-friday.sh` 固定运行时和网络参数，直接执行原版 `prepare-digest.js`，不要求用户配置 Telegram、邮件或 cron。原版使用的 CLAUDE_SKILL_DIR 也不再是当前云端入口的依赖。
3. **提示词。** 默认中文、最多 5 条精选，合并同一事件，注明快照时间和来源归属，提示上游缺失，旧播客注明日期；不把播放列表伪装成单集链接。不保存阅读记录，也不声称用户从没看过这些内容。
4. **尚未形成稳定模块。** 约 90 KB 的准备结果仍触发工具返回截断。原版发生一次临时输出目录越界阻断，模型改用工作目录后恢复；适配版发生工具参数错误和 shell 命令失败后重试，最终完成。Token 开销和等待时间仍偏大。
5. **行为约束主要来自提示词。** 默认 5 条有效，但适配版仍有约 2300 字符；它也提到了链接不完整的旧播客，虽说明了日期和原因，仍显冗长。现有入口没有程序级字数检查、每条数据的新鲜度策略、已读游标、发送确认或跨来源事件去重。
6. **上游仍是集中式快照。** 当前实现继续使用上游实时提供的摘要提示词，受其后续修改、数据错误、接口可用性与公开 API 限流影响。某一路请求抛异常时，原版 Promise.all 仍可能导致整个准备任务失败；本次成功调用不证明故障隔离已完善。

准备脚本返回 JSON 对象：`x` 是按作者分组的帖子数组（正文、ID、createdAt、URL、互动指标），`podcasts` 包含整篇 transcript，`blogs` 包含文章 content；另有 config、stats、errors、prompts。当前 32 条帖子正文合计 9655 字符，单篇播客 transcript 为 56644 字符；博客结构从上游代码确认，本次样本为空。

建议统一素材标识和日期，保留完整原文及各路错误；短帖批量交给模型做价值筛选和同事件归并，长播客/博客先提炼并按内容版本缓存，再生成整体简报。默认 5–8 条、正文约 600–900 字只作为拟议篇幅目标，支持按主题筛选、展开某条及播客详解。保存实际展示顺序以支持“第二条”追问；只有以后明确要求自动推送时再接 Heartbeat 和发送去重。不因单次超字数直接丢弃整份内容，优先让模型压缩。

这些数据是集中维护的公开快照，不是全网搜索，也不保证包含全部刚发布的推文。网页 ChatGPT 的插件适配只是解释过的可行路径，本次未制作插件、接入 MCP 或同步本地 Skill。
