# Friday 记忆管理与纠错、服务器健康摘要：开发设计

日期：2026-11-01（北京时间）  
状态：设计稿，尚未实现或上线。本文中的接口、阈值和排期均为建议，不代表线上已有能力。

## 1. 目标与范围

- **记忆管理与纠错**：让 Sir 用微信或网页查看 Friday 记得什么、了解依据、纠正错误、处理临时变化及归档指定记忆。沿用少记原则和现有个人数据隔离。
- **服务器健康摘要**：手动查询主机资源、指定服务及网站入口状态，给出有时间标记的简短结果。根据 Sir 的要求，**不检查天气预警、邮件或其他业务模块的最近成功时间和连续失败状态**，也不把它们加入自动告警。
- 本文只设计，未授权据此部署、重启、修改远端资源、发送测试消息或改动个人记忆。上线和实发测试需按当时的明确指令执行。

## 2. 现状与约束

- `internal/assistant/memory.go` 使用每实例私有目录中的 Markdown 文件保存长期／短期记忆，支持 list、get、create、update、archive、revision 并发校验；未来记忆可见但按起始时间适用。过期和归档项目默认不进入当前可见集合。
- `memory_source.go` 要求模型发起 create/update 时，来源为**当前真实前台用户消息中的原文**，正文与引用一致；后台内容、模型建议和旧对话不是写入依据。不能因新增纠错而削弱该边界。
- 现有界面及私有桥已提供记忆相关能力，须在实施前验证实际通路和权限。`platform/nativebridge/main.go` 对部分原生工具有特殊处理，网页写入身份的保护不能只假定与微信相同。
- 平台已有实例运行状态与 HTTP 健康接口；这些不是完整主机监控。Friday 位于隔离实例，不能假设它能读取宿主机状态。
- 当前的天气预警工作区改动是独立内容，不属于本设计的实施范围。不要覆盖或提交已有修改。

## 3. 记忆：用户体验

### 3.1 查看与解释

1. “你记得我的天气偏好吗？”：检索相关**有效**记忆，简要复述；找不到说没有找到，不用推测补全。条目较多时分页，默认不把全部私人信息写进单条微信。
2. “看看我的记忆”：按长期、当前短期和未来安排分组；过期／归档项仅在明确要求时展示，且标清状态和时间。网页可显示搜索和筛选。
3. “你为什么这么说？”：区分实际引用的记忆、业务配置、当前对话和模型推断。若本次使用依据没有记录，诚实说无法确定，不能用事后找到的相似记忆冒充当时依据。
4. 记忆详情显示内容、类别、适用时间、状态、最近修改时间，以及可用的来源说明。历史数据缺少来源则显示“来源不可用”。不默认展示完整历史会话或泄露内部路径。

### 3.2 修改、临时覆盖与忘记

- “你记错了，我希望天气播报详细一点”：定位明确的原条目，使用当前用户消息中完整、自包含的个人陈述作为更新正文，成功后简述结果。多个候选时先展示候选询问，不猜测。
- “只在本周详细一点”：依据北京时间解析明确的日历边界，写独立短期记忆，结束时间为排他边界，保留长期条目；期限不清时不猜。到期后不再作为当前偏好。
- “忘掉这条”：指代明确时归档指定条目，并说明不再作为当前记忆；多个候选时先询问。归档不等于物理删除，也不承诺清除备份或历史会话。
- 作息、提醒、天气预警等结构化配置由其所属模块负责，不能通过修改个人记忆声称改变了实际配置。
- 用户明确纠正且对象清楚时无需再问是否保存；常规自然对话沿用现有少记规则。不主动询问是否记住随口说的话。

### 3.3 追溯与撤销：建议分阶段

现有字段 `source_message_id` 可提供部分来源线索，不保证历史消息仍可访问，也不足以证明某次回答实际引用了它。第一阶段仅展示真实存在的来源元数据，不进行历史消息回填。

第二阶段可设计有限修改历史与撤销；**默认暂不启用，也不新增保存期限假定**。实施前需确定：是否保留旧正文、保存多久、谁可以查看、导出/备份如何处理、归档和彻底删除如何作用于历史。用户未决定前不将旧正文复制进新的持久化日志。若未来启用撤销，必须检查当前 revision，仅撤销目标版本且重新验证授权，不能恢复已过期/已归档内容并暗中使之生效。

## 4. 记忆：实现设计

1. 扩展已有工具和前台提示策略，优先复用 `assistant_memory`、现有网页入口和各实例 home；不要建立第二份记忆数据库。
2. 读取层返回明确的 `active`、`future`、`expired`、`archived` 状态及来源可用性；以 `Asia/Shanghai` 展示日期，内部保留精确时间和排他到期语义。查询必须按当前实例身份限制，不接受用户传入 home 路径或 owner。
3. 纠错流程：读取候选 → 根据本轮上下文选择明确条目 → 取最新 revision → 用本轮真实用户原话和适当类别调用现有写入路径 → 返回结果。冲突时重新读取并让用户判断，不自动覆盖。
4. 现有 `body == source_quote` 约束继续生效。像“把它改成详细一点”这样依赖指代、无法形成自包含事实的消息，不能从旧记忆拼成一段后冒充本轮原话；应请求用户提供完整表述，或另行设计可验证的结构化纠错协议后再实现，不能绕过来源校验。
5. 临时覆盖需建立明确的主题关联和冲突规则：同一主题临时项在适用时间内优先；若多个有效项冲突且无法判断，以不确定处理，不自动删除任何条目。当前系统是否已有可安全复用的主题关联机制需实施时确认；不要依赖模型猜测建立永久关联。
6. 区分“记忆来源”和“本次回答依据”。若要可靠解释具体回答，需在回答生成时记录实际引用的最小标识、版本及上下文，绑定消息与实例；当前没有证据证明已有完整引用追踪。此功能先设计为可选能力，无法证明时答“无法确定”。不为解释而记录额外正文。
7. 网页操作复用现有认证、用户隔离、CSRF 及版本校验；明确区分用户直接编辑与模型工具写入，审查私有桥授权通路，不能将网页操作冒充聊天原话。归档同样必须确认当前前台身份、条目归属与 revision。
8. 写入失败、revision 冲突、找不到条目时不得回复“已修改”。不从过期或归档内容自动恢复记忆。

### 4.1 验收场景

- 查看有记录／无记录、当前／未来／过期／归档，来源缺失；不跨实例读取。
- 清楚的永久纠错、明确期限的临时变更、缺少期限、多个同主题候选；临时项到期不影响长期项。
- 用户否定、引用、假设、外部内容和后台消息不触发未经授权写入；原文约束与 negation 测试继续通过。
- 网页与微信并发修改同一 revision；冲突不覆盖，失败不声称成功。
- 归档后常规上下文不可见，历史查看明确标识状态；来源不存在时不伪造依据。
- 单元测试覆盖时间和权限边界；集成测试使用隔离 home、模拟微信及模型；无需触及真实个人记忆。

## 5. 服务器健康：用户体验

第一阶段仅主动查询，例如“Friday，服务器现在怎么样？”建议回复：总体状态、检查时间、资源概况、指定服务与网站入口；只展开异常和未知项。需要细节时才显示具体数值。

**示例，非实时数据：**“Sir，21:30 的检查显示服务器运行正常：磁盘剩余 32%，内存使用率 58%，Friday 和网站入口正常。”若接口不可用，应说“服务器状态暂时无法读取”，不能说正常。

| 指标 | 第一阶段建议 | 判断边界 |
| --- | --- | --- |
| 主机资源 | 根文件系统可用空间及百分比、内存可用/总量、1/5/15 分钟负载及 CPU 逻辑核数 | 显示实际采样时间；负载不等同于 CPU 使用率。磁盘指标限定具体挂载点。 |
| 固定服务 | Friday 实例、AS Robot 容器及部署时确认的必要服务 | 仅报告采集器实际看到的状态；容器或 systemd active 不证明业务可用。 |
| 固定网站入口 | 配置的 HTTPS 健康地址，检查响应状态和超时 | 状态码仅证明该入口当时响应，不证明微信可达或其他功能正常。 |

不检查天气预警、邮件或其他业务模块健康；不读取消息正文、个人记忆、访问日志、密钥或环境变量。不将“配置了微信”说成“微信已连接/消息已送达”。

## 6. 服务器健康：采集与安全设计

### 6.1 架构

建议宿主提供**单独的只读采集器**，从固定来源获取指标，输出版本化 JSON；Friday 通过专用、鉴权的本地接口读取。具体采用 Unix socket、受限本地代理或现有桥复用，应先按实例隔离与可维护性做最小权限评估，不能预设隔离容器能访问宿主 socket。

- 采集器采用专用低权限身份，仅访问完成固定检查必要的系统接口；服务与容器观察权限需明确评估，避免把 Docker socket 等同于只读安全权限。
- 固定白名单配置由管理员在宿主维护；模型和普通用户不能传命令、任意路径、URL、服务名、容器名或身份，也不能执行重启、停止、删除、配置修改。
- 网站只允许管理员配置的固定 HTTPS 目标，验证 TLS，限制超时、重定向和响应大小；查询不返回页面正文。
- 快照字段建议：`schema_version`、`collected_at`、各项 `status`、`value`、`unit`、`checked_at`、安全的错误类别。状态限定 `ok` / `warning` / `critical` / `unknown`；无权限、超时、数据过期均为 unknown，而非正常。
- 各项独立超时与失败，不让单项阻塞全报告；检查频率有上限。缓存过期时显示采集时间及 unknown，不用旧结果装作实时。
- 输出使用用户看得懂的名称，隐藏主机路径、账号、网络拓扑和敏感异常细节；管理员调试细节与用户摘要分离。
- 采集器和 Friday 之间的鉴权、权限、并发、日志与故障重连需在实现时依据实际部署验证。采集器异常不能影响既有 Friday 主流程。

### 6.2 阈值和总体状态

优先只读展示实际数值，阈值不得伪装为已验证的健康标准。部署前在真实主机上只读观察资源基线，再确定各项阈值、采样间隔和快照最大年龄；设计阶段不擅自设置生产默认值。

建议汇总规则：任一关键项 critical → 异常；否则任一 warning → 需关注；否则关键项有 unknown → 状态不完整；全部关键项 ok → 正常。关键项由固定配置定义，必须至少一个；没有配置或没有数据不能得出正常。非关键项 unknown 也需在详情中可见。

### 6.3 自动通知为后续可选项

第一阶段不新增周期性微信推送。后续如需要，由 Sir 明确选择是否启用、检查频率、连续失败次数、恢复通知与去重时间；默认服从现有作息和发送前门控，不在窗口外补发旧事件。持久化告警状态以防重复，但不能把发送 API 接受当成用户已读。

自检不能发现采集器、Friday 或整机同时失效。需要整机宕机通知时，应单独设计外部监测和独立通知链路；本方案不声称已具备此能力。

### 6.4 验收场景

- 模拟资源正常、接近阈值、超过阈值、磁盘不可读取及指标过期；对未知不报正常。
- 模拟服务停止、名称不在白名单、接口失败、网站超时、TLS 失败、单项失败及空配置。
- 验证未授权请求被拒、实例不可越权、无法指定命令/URL/路径，且不能修改宿主状态。
- 验证汇总级别和采集时间、故障时限、缓存与并发限制；不依赖天气/邮件业务状态。
- 隔离环境测试和模拟接口通过后，另行安排只读生产核验；是否启用后台周期采集、上线与实际发送均遵循当时授权。

## 7. 分阶段交付与实施前决策

1. **记忆查看与纠错**：盘点现有前台、网页入口与测试；实现状态展示、明确来源提示、歧义澄清及安全纠错；验证后交付。
2. **健康摘要主动查询**：确定受监控的精确服务和网站、采集权限及部署路径；实现隔离采集和结构化摘要；在测试环境验证。
3. **可选增强**：在决定历史保留政策后实现修改历史/撤销；在决定检查频率、阈值、作息及通知行为后实现自动健康提醒。外部监测另行设计。

依赖用户决定：需要列入哪些额外服务；是否启用修改历史及其保留/删除政策；是否需要自动提醒及其规则。第一阶段可先围绕已明确的 Friday、AS Robot 和网站入口设计，精确单位和实际资源需部署前只读核实。

## 8. 发布与回退原则

实现前重新检查分支、未提交修改、真实运行实例及依赖，隔离测试数据，不覆盖现存工作。提供迁移兼容策略：旧记忆和缺少来源的条目仍可读取；不得自动批量改写或归档。发布前确认备份与回退步骤并记录版本、健康状态和验收结果；对远端文件、服务或部署的变更按当时的明确授权执行。回退应保留实施期间用户新增数据，不能简单用旧备份覆盖新数据。
